## 4. Failures found and improvements made

| Failure found | How it was found | Fix |
|---|---|---|
| Pipe-delimited logs parsed as generic key=value, losing service and trace ids | dialect unit test | dialect regex accepts the leading `|`; each log file now resolves to exactly one dialect |
| Strong identifier links alone found 76% of sample resources | linking recall on samples | workflow links from deletion-worker events in the request window + global one-owner assignment (93%) |
| Overlapping request windows gave accounts to the wrong case | per-case link diffs | match account jobs to the workflow by its reported status (a matching feature, never proof) |
| Snapshot bundles captured after audit_at leaked in through their internal timestamps | evidence accuracy 53% | eligibility uses the manifest capture time |
| Partial bundles 'proved' other people's records absent | retained audit records reported missing | bundle absence only counts for subjects the bundle includes; SQL dumps are full captures |
| A primary-side capture hid a failover ghost copy | case_05 | state is tracked per location; present in any location means present |
| A catalog link was treated as proof a record exists | extra steps for `object_19`, `tombstone_17` | activity fallback only uses state-changing events |
| Retained security records without evidence were dropped | missing VERIFY_RECORD_PRESENT steps | account and retained records are always planned; partial captures never prove their absence |
| A case with nothing verifiable would be claimed COMPLETE | validator: COMPLETE without steps | unproven required states keep a case INCOMPLETE |
| Older explicit absences outranked a later sighting of the record | custom case `earlier-cleanup-counts` | only absences after the last sighting can prove deletion |
| Vision model wrote `user_11 - account_5762` into one field; strict validation dropped the id | screenshot probe | ids extracted with the evidence regexes; referenced records kept as linked sightings |
| Undocumented free-tier cap of 1,000 output tokens/minute (429) and a dense screen truncating at the token limit (400) | live ledger | output-token window in the guard; compact retry; truncation cached so it is never repeated |
| Intent batches of 25 silently dropped the last items at the token limit | items answered vs asked | batches of 30 with a minimal schema, and a second round re-asks any skipped item |
| Custom cases about the same person saw each other's added evidence (2 false failures) | custom-case results | each custom case runs on its own isolated dataset copy |
| Ties were flagged for every case whose window held the event (315 of 392 links), hiding which were really undecidable | tie analysis | `contested-with` lists only rivals with the same result evidence that lack, or could swap, a record of that kind |

## 5. Tie-breaking analysis (records with no identifiers left)

Deleted accounts and anonymized analytics carry no identifier, so they are tied to a case through
deletion-worker events in the request window. Cases sharing a report batch compete for them. Each
candidate signal was measured on strongly linked records only (pseudo-labels, not sample answers):

| Signal | Measurement | Verdict |
|---|---|---|
| Deletion job result vs the workflow's reported status | 253/255 match (99.2%) | **used**, for every deletion job |
| Batch order follows requested_at | agrees on 49% of 166 pairs (50% = chance) | no signal |
| Batch order follows case number | agrees on 49% of 166 pairs (50% = chance) | no signal |
| Batch order follows user number | agrees on 51% of 166 pairs (50% = chance) | no signal |
| Batch order follows email | agrees on 54% of 166 pairs (50% = chance) | no signal |
| Nearest record in the same evidence file has the same owner | 8% vs 8% by chance (2624 records) | no signal (files are ordered by id or interleave people) |
| Anonymized analytics content (products, metrics) matches the subject's other records | 8 product names in the whole dataset | no signal |

Other job types (anonymize, redact, disable, block) always report SUCCESS, so they carry no result
signal either. When subjects with the same result evidence compete, the linker assigns
deterministically and records `contested-with=[...]` on the link.

| Split | Workflow links | Contested, 2 claimants | 3 | 4+ |
|---|---|---|---|---|
| sample | 23 | 6 | 2 | 1 |
| eval | 369 | 110 | 84 | 34 |

A contested link is right with probability about 1/k. Dropping links with k >= 3 would raise step
precision but guarantee a miss on records the answer always contains (every case verifies its
account), so all links are kept. This is the measured ceiling of identity linking on this data,
not a parameter tuned to the samples.
